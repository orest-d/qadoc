# Questionnaire Library Specification V2

## 1. Purpose

This document specifies version 2 of the browser-only questionnaire library.

Version 2 keeps the v1 question data model largely compatible, but changes the operating philosophy:

- the browser app should be able to import, edit, export, and save questionnaires without requiring Python tooling,
- questions should be represented internally and externally as a flat tabular collection,
- the host HTML should own the application shell, header, pages, mode labels, and templates,
- JavaScript should provide a documented API that the host HTML can use to build its own UI,
- the runtime should support editor workflows as a first-class mode.

The library must run entirely in the browser. No server component is required.

Python build tools may still exist to assemble a standalone HTML file, but once the app is assembled they should be optional for day-to-day questionnaire editing and data exchange.

## 2. Compatibility With V1

V2 should remain largely compatible with v1 question objects.

The following v1 fields should continue to work with the same meaning:

- `id`
- `type`
- `prompt`
- `title`
- `description`
- `help`
- `required`
- `default`
- `allow_freetext`
- `multiline`
- `textarea_rows`
- `predefined_text`
- `options`
- `visible_if`
- `rule_on_value`
- `rule_status`
- `reviewer_question`
- `answer`
- `review_status`
- `review_status_by_rule`
- `reviewer_comment`

The main data-shape change is that v2 treats questions as a flat list of rows. Page membership and order are stored on each question row instead of being implied by nested `pages[].questions[]` arrays.

V2 implementations should be able to import v1 nested JSON and normalize it into the v2 flat model.

Persisted v2 question fields must use `snake_case`. V1 camelCase fields should be accepted as import aliases for compatibility, but exports should use snake_case.

Compatibility aliases include:

- `predefinedText` -> `predefined_text`
- `visibleIf` -> `visible_if`
- `questionId` inside visibility conditions -> `question_id`
- `notEquals` inside visibility conditions -> `not_equals`
- `isOther` inside options -> `is_other`

## 3. Goals

- Provide a lightweight embeddable `javascript + css` library.
- Run entirely in static HTML with no backend.
- Use a flat tabular question format as the primary import/export format.
- Import and export questions as CSV directly from the browser.
- Import and export questions as JSON directly from the browser.
- Provide a migration script that converts old nested v1 questionnaire files to the v2 flat format.
- Preserve unknown extra question fields during import/export.
- Allow top-level questionnaire metadata to be configured programmatically in HTML.
- Allow page definitions and page order to be configured programmatically in HTML.
- Allow display names for modes to be configured programmatically in HTML.
- Expose a documented API for mode switching, page navigation, loading, saving, and answer access.
- Support a hook that runs on every user change for ad hoc visibility, rules, and derived values.
- Support `interviewed`, `reviewer`, and `editor` modes.
- Allow question card rendering to be customized through templates.
- Allow the application shell and questionnaire header to be defined in host HTML rather than generated by the library.

## 4. Non-Goals

- No backend, database, or remote API.
- No authentication or user management.
- No collaborative real-time editing.
- No requirement for a JavaScript build toolchain.
- No requirement that all questionnaire UI be generated by the library.
- No requirement that host applications use the default templates.

## 5. Actors And Modes

### 5.1 Interviewed

The interviewed mode is for the person answering ordinary questionnaire questions.

In interviewed mode:

- normal questions are shown,
- `reviewer_question: true` questions are hidden,
- answer controls are editable,
- review controls are hidden or disabled.

### 5.2 Reviewer

The reviewer mode is for validation, review, and reviewer-only questions.

In reviewer mode:

- normal questions are shown with answers visible,
- normal answer controls are read-only by default,
- `reviewer_question: true` questions are shown and answer controls are editable,
- review controls are shown for questions with `has_status !== false`,
- review status labels and mode names may be configured by the host application.

### 5.3 Editor

The editor mode is for changing the questionnaire definition itself.

In editor mode, the app must allow an authorized local user to:

- edit existing question rows,
- rearrange questions,
- add new questions,
- delete questions,
- edit page assignment and question order,
- import questions from CSV or JSON,
- export questions to CSV or JSON.

Question editing should be presented as a form. The form should include the standard fields and should allow extra fields to be retained and edited where practical.

### 5.4 Configurable Mode Names

The internal mode ids should be stable:

- `interviewed`
- `reviewer`
- `editor`

The displayed labels must be configurable in HTML. For example, `reviewer` may be displayed as `Validator`.

Example:

```js
const app = QuestionnaireV2.create({
  modeLabels: {
    interviewed: "Applicant",
    reviewer: "Validator",
    editor: "Designer"
  }
});
```

## 6. High-Level Architecture

The solution consists of:

- a browser JavaScript library,
- a default CSS stylesheet,
- host HTML that defines the application shell,
- host-provided templates for question cards and editor forms,
- optional Python or build-time tooling for assembling a single HTML file.

The JavaScript library should manage:

- normalized questionnaire data,
- question rendering into host-selected containers,
- answer state,
- review state,
- page navigation,
- mode switching,
- import/export,
- editor operations,
- hooks and change notifications.

The host HTML should define:

- the questionnaire header,
- toolbar layout,
- mode switch controls,
- page navigation controls,
- import/export buttons,
- app containers,
- templates.

## 7. Configuration Model

Top-level questionnaire parameters and page parameters should be configured programmatically in the HTML file.

### 7.1 Top-Level Parameters

The host application may provide:

```js
const questionnaireConfig = {
  id: "onboarding-review",
  title: "Project Onboarding Questionnaire",
  version: "2.0",
  metadata: {
    owner: "Example Team",
    locale: "en"
  }
};
```

Top-level parameters should be included when exporting full questionnaire JSON. CSV export may include them in a sidecar JSON export or an optional metadata preamble if the implementation supports that.

### 7.2 Pages

Pages should be configured separately from questions.

Each page definition may include:

- `id`
- `title`
- `description`
- `order`
- extra host-defined page fields.

Example:

```js
const pages = [
  { id: "basics", title: "General Information", description: "Baseline details.", order: 10 },
  { id: "details", title: "Supporting Details", description: "Follow-up questions.", order: 20 }
];
```

Question rows refer to pages only through `page_id`.

Questions must not carry `page_title` or other page presentation fields. Page titles, descriptions, and ordering belong to the page configuration in host HTML or the full JSON/YAML `pages` section.

If a question has no `page_id`, it is assigned to a page with `id: "default"`.

If a question references a `page_id` that is not present in the configured pages, the runtime should create a page with:

- `id` equal to the referenced `page_id`,
- `title` equal to the referenced `page_id`,
- empty `description`,
- order after configured pages.

If the normalized questionnaire has only one page, typically `default`, page navigation controls should not be shown by the default UI. Host HTML may still choose to show custom page controls.

The page list and page order should be configurable in HTML and should not require editing the JavaScript source.

### 7.3 Question Field Configuration

The set of question attributes should be configurable programmatically in the host HTML. This is the typical v2 scenario: the app defines which fields exist, how they are labeled in editor mode, how they are parsed during import, and whether they are shown in templates.

Example:

```js
const questionFields = [
  { name: "id", label: "Question ID", type: "text", required: true },
  { name: "page_id", label: "Page", type: "page_id", default: "default" },
  { name: "prompt", label: "Prompt", type: "textarea" },
  { name: "type", label: "Type", type: "select", options: ["text", "checkbox", "radio", "dropdown", "info", "html"] },
  { name: "has_status", label: "Has review status", type: "boolean", default: true }
];
```

The runtime should provide defaults for the standard fields, but host configuration should be able to add extra fields and control how they appear in editor forms and import/export workflows.

#### Default Editor UI For Standard Fields

The default question editor should use the following field configuration when the host application does not override it.

| Field | Default editor UI | Notes |
| --- | --- | --- |
| `id` | text input | Required. Should validate uniqueness. |
| `page_id` | page select with text fallback | Defaults to `default`. Unknown values create pages. |
| `order` | number input | Used for ordering within a page. |
| `type` | select | Default options: `checkbox`, `radio`, `dropdown`, `text`, `info`, `html`. |
| `prompt` | textarea | Primary question text. |
| `help` | textarea | Optional help text. |
| `required` | checkbox | Boolean. Applies only when the question is visible and editable. |
| `default` | text input | The editor may switch to checkbox/value-specific controls based on question type. |
| `allow_freetext` | checkbox | Boolean. |
| `reviewer_question` | checkbox | Boolean. Hidden from interviewed mode and editable in reviewer mode. |
| `has_status` | checkbox | Boolean. Defaults to `true`. |
| `multiline` | checkbox | Boolean. |
| `textarea_rows` | number input | Minimum 1. Recommended default 4. |
| `options` | JSON textarea plus optional structured option editor | Stored as an array in JSON and JSON string in CSV. Option fields use snake_case, such as `is_other`. |
| `visible_if_question_id` | question select with text fallback | Used for simple flattened visibility. |
| `visible_if_operator` | select | Default options: empty, `equals`, `not_equals`, `contains`. |
| `visible_if_value` | text input | Parsed according to simple value parsing rules. |
| `visible_if` | JSON textarea | Complex visibility expression, using snake_case keys such as `question_id` and `not_equals`. |
| `rule_on_value` | text input | Simple rule trigger value. |
| `rule_status` | status select | Default options: empty, `pending`, `satisfactory`, `partial`, `unsatisfactory`. |
| `answer` | textarea or type-specific editor | Runtime value. Editor may expose this in an advanced/state section. |
| `review_status` | status select | Hidden or disabled when `has_status` is `false`. |
| `review_status_by_rule` | read-only checkbox | Runtime flag. |
| `reviewer_comment` | textarea | Runtime reviewer note. |

The default editor form should group fields into practical sections:

- identity and placement: `id`, `page_id`, `order`, `type`,
- content: `prompt`, `help`,
- behavior: `required`, `default`, `allow_freetext`, `reviewer_question`, `has_status`, `multiline`,
- advanced behavior: `textarea_rows`, `options`,
- visibility and rules: `visible_if_*`, `visible_if`, `rule_on_value`, `rule_status`,
- state: `answer`, `review_status`, `review_status_by_rule`, `reviewer_comment`.

Host editor templates should mark always-visible sections with a class such as `is-essential` and collapsible sections with a class such as `is-advanced`. The advanced settings UI state is renderer state only and must not be serialized into CSV or JSON question data.

Host applications may hide the state section for questionnaire design workflows, but import/export must still preserve those fields.

## 8. Flat Question Data Format

V2 uses a flat array of question rows as the primary data model.

Example:

```json
[
  {
    "id": "q_country",
    "page_id": "basics",
    "order": 20,
    "type": "dropdown",
    "prompt": "Select your country",
    "required": true,
    "default": "",
    "allow_freetext": true,
    "options": "[{\"value\":\"no\",\"label\":\"Norway\"},{\"value\":\"se\",\"label\":\"Sweden\"}]",
    "visible_if_question_id": "",
    "visible_if_operator": "",
    "visible_if_value": "",
    "rule_on_value": "other",
    "rule_status": "partial",
    "answer": null,
    "has_status": true,
    "review_status": "pending",
    "review_status_by_rule": false,
    "reviewer_comment": ""
  }
]
```

### 8.1 Standard Question Fields

The standard flat row fields are:

- `id`
- `page_id`
- `order`
- `type`
- `prompt`
- `title`
- `description`
- `help`
- `required`
- `default`
- `allow_freetext`
- `multiline`
- `textarea_rows`
- `predefined_text`
- `options`
- `visible_if_question_id`
- `visible_if_operator`
- `visible_if_value`
- `visible_if`
- `rule_on_value`
- `rule_status`
- `reviewer_question`
- `has_status`
- `answer`
- `review_status`
- `review_status_by_rule`
- `reviewer_comment`

Implementations may add more fields. Unknown fields must be preserved by import/export and made available to templates.

### 8.2 Non-Flat Data In CSV

CSV is flat. Non-flat question data must be represented in one of two ways:

1. Flattened columns for common structures.
2. A string containing JSON for complex structures.

Recommended mappings:

- `options` should be a JSON string containing an array of option objects.
- simple visibility may use `visible_if_question_id`, `visible_if_operator`, and `visible_if_value`.
- complex visibility may use `visible_if` as a JSON string.
- simple rule-based review may use `rule_on_value` and `rule_status`.
- complex ad hoc rules should be implemented by the host `onChange` hook or stored in extra fields consumed by that hook.

### 8.3 Options Format

In JSON exports, `options` may be either:

- an array of option objects,
- or a JSON string that parses to an array of option objects.

In CSV exports, `options` should be a JSON string.

Each option may include:

- `value`
- `label`
- `is_other`
- extra option fields.

### 8.4 Visibility Format

Simple visibility may be flattened:

```csv
id,visible_if_question_id,visible_if_operator,visible_if_value
q_accountant_name,q_accounting_support,equals,true
```

Supported simple operators should include:

- `equals`
- `not_equals`
- `contains`

Complex visibility may be stored in `visible_if` as JSON:

```json
{
  "all": [
    { "question_id": "q_employment_status", "equals": "self_employed" },
    { "question_id": "q_accounting_support", "equals": true }
  ]
}
```

### 8.5 Rule Format

Simple rule-based status uses:

- `rule_on_value`
- `rule_status`

If `review_status` is `pending` and the current answer equals `rule_on_value`, then `review_status` becomes `rule_status` and `review_status_by_rule` becomes `true`.

If a rule does not apply, `review_status_by_rule` is `false`.

Manual reviewer changes clear `review_status_by_rule`.

More complex rules should be implemented in the `onChange` hook.

### 8.6 Extra Fields

Question rows may contain extra fields not defined by this specification.

The runtime must:

- preserve extra fields during import/export,
- keep extra fields attached to the question object,
- expose extra fields to question templates,
- allow editor mode to display or edit extra fields where configured.

## 9. Question Types

The library must support at least:

- `checkbox`
- `radio`
- `dropdown`
- `text`
- `info`
- `html`

### 9.1 Checkbox

A checkbox question represents a boolean answer.

Unlike v1, checkbox rendering must not repeat the question prompt as both the card heading and the checkbox label by default.

The checkbox label should be configurable through an option or field.

Recommended fields:

- `checkbox_label`
- or `options` containing one option object with a `label`.

If no checkbox label is defined, the implementation may render the checkbox control without a repeated text label, using the prompt as the accessible label.

### 9.2 Radio And Dropdown

Radio and dropdown questions use `options`.

`allow_freetext` may enable a companion free-text input when the selected option has `is_other: true`.

### 9.3 Text

Text questions render an input or textarea depending on `multiline`.

`textarea_rows` may control textarea height.

### 9.4 Info

`info` is display-only.

It renders the current answer value in a `<pre>` block.

This may be used to:

- provide extra guidance to interviewed users,
- show derived values calculated by hooks,
- display structured text output.

`info` does not require an editable answer control.

### 9.5 HTML

`html` is display-only.

It renders the current answer value inside a `<div>`.

This may be used to:

- provide rich guidance,
- show derived values with formatting,
- embed host-controlled HTML snippets.

Implementations must document sanitization behavior. If arbitrary imported HTML is rendered, the host application must understand the security implications. The recommended default is to treat trusted host-authored HTML as allowed and imported untrusted HTML as escaped unless explicitly enabled.

## 10. Review Model

### 10.1 Status Support

Questions may or may not have review status.

`has_status` controls whether a question has status controls.

- If `has_status` is `true` or omitted, status controls are available in reviewer/editor contexts.
- If `has_status` is `false`, review status controls are hidden and status validation/rules are skipped unless the host hook chooses otherwise.

Default statuses should include:

- `pending`
- `satisfactory`
- `partial`
- `unsatisfactory`

The host application may configure labels and colors.

### 10.2 Reviewer-Only Questions

`reviewer_question` controls role visibility and editability.

- `false` or omitted: the question appears to both interviewed and reviewer roles, but reviewer answer controls are read-only by default.
- `true`: the question is hidden from interviewed mode and shown to reviewer mode with editable answer controls.

Reviewer-only questions otherwise behave like ordinary questions, including rules, derived values, import/export, templates, and editor mode.

## 11. Templates And Appearance

V2 should not hard-code the application header or full shell in JavaScript.

### 11.1 Host-Owned Shell

The host HTML should define:

- header markup,
- title placement,
- toolbar buttons,
- mode selector,
- page navigation,
- import/export controls,
- render target containers.

The library API should make it easy for those controls to call runtime functions.

### 11.2 Question Card Templates

Question cards should be defined as templates.

Supported template sources should include at least one of:

- invisible DOM nodes in HTML, such as `<template id="question-card-template">`,
- Mustache-style string templates.

The template context should include:

- all question fields,
- extra question fields,
- answer value,
- review data,
- current mode,
- visibility state,
- validation errors,
- page information.

Changing the question card template should be enough to display extra fields without changing core renderer code.

### 11.3 Editor Templates

Editor forms should also be template-driven or configurable.

At minimum, editor mode should provide fields for:

- standard question fields,
- page assignment,
- order,
- options as JSON text,
- visibility fields,
- rule fields,
- extra fields.

## 12. Hooks And Derived Behavior

The runtime must support a hook executed on every user change.

Example:

```js
const app = QuestionnaireV2.create({
  onChange(event, api) {
    const income = Number(api.getAnswer("q_income") || 0);
    const expenses = Number(api.getAnswer("q_expenses") || 0);
    api.setAnswer("q_balance_info", JSON.stringify({ balance: income - expenses }, null, 2), {
      silent: true
    });

    if (income - expenses < 0) {
      api.setReviewStatus("q_balance_info", "partial", { byRule: true, silent: true });
    }
  }
});
```

The hook should receive:

- event type,
- question id,
- changed field,
- previous value,
- new value,
- current mode,
- access to the public API.

The hook may be used to:

- evaluate ad hoc rules,
- calculate derived values,
- modify visibility,
- update `info` and `html` questions,
- update reviewer statuses,
- enforce local business logic.

Implementations should support a `silent` option for API calls made inside hooks to prevent infinite loops.

## 13. Browser Import And Export

The browser app must support import/export without Python tools.

### 13.1 CSV Import

CSV import must:

- parse a header row,
- map columns to question fields,
- preserve unknown columns as extra fields,
- parse booleans and numbers where known fields require them,
- parse JSON-string fields such as `options` and `visible_if` where appropriate,
- report row-level errors clearly.

### 13.2 CSV Export

CSV export must:

- export a flat question table,
- include standard fields,
- include extra fields,
- serialize non-flat values such as `options` and `visible_if` as JSON strings,
- preserve enough information to re-import the questionnaire.

### 13.3 JSON Import

JSON import must support:

- v2 flat question arrays,
- v2 full questionnaire objects,
- v1 nested questionnaire objects where pages contain questions.

### 13.4 JSON Export

JSON export should support:

- flat question array only,
- full v2 object with top-level metadata, pages, and flat questions,
- optionally v1-compatible nested structure.

### 13.5 HTML Save

Standalone HTML export may serialize the current document and replace embedded data blocks with current top-level config, page config, and flat question data.

The embedded JSON must be escaped so it cannot terminate script blocks.

### 13.6 Migration Script

The project should include a Python migration script for converting old v1 nested questionnaire files into the v2 flat format.

The script must support at least YAML input. JSON input is recommended.

The output format should be selected from the output file extension:

- `.csv` writes a flat question table,
- `.json` writes a full v2 object with `config`, `pages`, and `questions`,
- `.yaml` or `.yml` writes the same full v2 object in YAML.

The converter should normalize v1 camelCase question fields to v2 snake_case fields, including `predefinedText` to `predefined_text`, `visibleIf` to `visible_if`, option `isOther` to `is_other`, and visibility condition `questionId` to `question_id`.

## 14. Public API

The API must be documented and stable enough for host HTML to build custom controls.

Example initialization:

```js
const app = QuestionnaireV2.create({
  questions,
  pages,
  config,
  mode: "interviewed",
  modeLabels: {
    interviewed: "Interviewed",
    reviewer: "Reviewer",
    editor: "Editor"
  },
  containers: {
    questions: document.getElementById("questions"),
    pageNav: document.getElementById("page-nav")
  },
  templates: {
    questionCard: document.getElementById("question-card-template"),
    editorForm: document.getElementById("question-editor-template")
  },
  onChange(event, api) {
    // host logic
  }
});
```

### 14.1 Mode API

Required methods:

```js
app.getMode();
app.setMode("reviewer");
app.getModeLabels();
app.setModeLabels({ reviewer: "Validator" });
```

### 14.2 Page API

Required methods:

```js
app.getPages();
app.setPages(pages);
app.getCurrentPage();
app.setPage("details");
app.nextPage();
app.previousPage();
```

Page normalization must follow the same rules as the data model:

- missing question `page_id` values are treated as `default`,
- unknown referenced `page_id` values create pages whose title is the same as the id,
- default page controls are hidden when there is only one normalized page.

### 14.3 Question API

Required methods:

```js
app.getQuestions();
app.setQuestions(questions);
app.getQuestion("q_country");
app.updateQuestion("q_country", { required: false });
app.addQuestion(question);
app.deleteQuestion("q_country");
app.moveQuestion("q_country", { page_id: "details", order: 30 });
```

### 14.4 Answer API

Required methods:

```js
app.getAnswer("q_country");
app.setAnswer("q_country", "no");
app.getAnswers();
app.setAnswers({ q_country: "no", q_notes: "..." });
```

### 14.5 Review API

Required methods:

```js
app.getReviewStatus("q_country");
app.setReviewStatus("q_country", "satisfactory", { byRule: false });
app.getReviewerComment("q_country");
app.setReviewerComment("q_country", "Looks good.");
```

Questions with `has_status: false` should return `null` or an equivalent documented value for review status.

### 14.6 Import/Export API

Required methods:

```js
app.loadCsv(csvText);
app.exportCsv();
app.loadJson(jsonTextOrObject);
app.exportJson({ format: "full" });
app.exportJson({ format: "flat" });
app.exportJson({ format: "v1-nested" });
app.saveJsonFile(filename);
app.saveCsvFile(filename);
app.saveHtmlFile(filename);
```

### 14.7 Rendering API

Required methods:

```js
app.render();
app.renderQuestions();
app.renderPageNav();
app.renderEditor();
app.refreshVisibility();
app.validate();
```

The host HTML should be able to wire buttons directly to these functions.

## 15. Editor Mode Requirements

Editor mode must support:

- adding a question,
- editing a question,
- deleting a question,
- reordering questions,
- assigning questions to pages,
- editing options as structured data or JSON text,
- editing visibility rules,
- editing rule fields,
- editing `reviewer_question`,
- editing `has_status`,
- preserving extra fields.

The editor should use forms rather than raw JSON as the primary UI.

Implementations may also offer raw JSON editing for advanced users.

## 16. Validation

The runtime must validate:

- question ids are unique,
- referenced page ids exist or can be created,
- referenced question ids in visibility conditions exist,
- radio and dropdown questions define valid options,
- required visible questions are answered,
- JSON strings in CSV fields parse correctly,
- `rule_status` values are known if status labels are restricted,
- `has_status: false` questions do not require status,
- loaded v1 nested structures can be normalized or produce clear errors.

Validation errors should be available through the API and displayable by templates.

## 17. Accessibility

The rendered questionnaire should follow basic accessibility requirements:

- labels associated with inputs,
- keyboard-accessible navigation,
- semantic grouping of radio options,
- visible indication of required fields,
- readable focus states,
- accessible editor forms,
- accessible import/export controls,
- accessible status controls.

Templates supplied by host applications should preserve these requirements.

## 18. Styling

The default stylesheet should remain professional, clean, and simple.

The host application should be able to override appearance by:

- replacing templates,
- adding CSS,
- setting CSS variables,
- configuring status colors,
- configuring mode labels and shell text in HTML.

V2 should avoid requiring JavaScript changes for visual rearrangement of headers, toolbars, or question card contents.

## 20. Acceptance Criteria

The specification is satisfied when:

1. A static HTML page can embed the library without a build step.
2. The library can initialize from flat question rows.
3. The library can import v1 nested JSON.
4. The library can import and export CSV in the browser.
5. The library can import and export JSON in the browser.
6. Unknown extra question fields survive import/export.
7. Pages are configured in host HTML and questions are assigned to pages by `page_id`.
8. Mode labels are configurable in host HTML.
9. Host HTML can use documented API methods for mode switching, page navigation, loading, saving, and answer access.
10. The `onChange` hook runs on every user change and can update derived values.
11. `info` questions render answer text in a `<pre>`.
12. `html` questions render answer HTML in a `<div>` with documented sanitization behavior.
13. The application shell and header can be defined in HTML rather than generated by JavaScript.
14. Question cards can be rendered through host-provided templates.
15. Editor mode can add, edit, delete, and reorder questions using forms.
16. `reviewer_question` controls reviewer-only visibility and editability.
17. `has_status` controls whether a question has review status.
18. Checkbox questions do not repeat the prompt as a checkbox label unless configured to do so.
