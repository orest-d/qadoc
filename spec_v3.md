# Questionnaire Library Specification V3

## 1. Purpose

This document specifies version 3 of the browser-only questionnaire library.

Version 3 builds on the v2 philosophy — browser-native, no build step, host-HTML-owned shell — and introduces several improvements:

- a simplified, cleaned-up question data model,
- new question types that cover common conditional-input patterns,
- a clear separation between **role** (who the user is) and **view** (how data is presented),
- a reviewer scoring model with weighted status summary,
- reviewer comments visible to interviewed users,
- an anchor-based navigation system for deep linking and browser history,
- a tabular editor view with column grouping and inline editing,
- a template editor view with syntax-highlighted editing of Mustache templates and the `onChange` hook,
- Mustache.js as the rendering engine (replacing the v2 pseudo-Mustache implementation).

The library must run entirely in the browser. No server component is required.

## 2. Migration From V1 and V2

V3 is not backward-compatible with the v2 data model. A Python migration script (`convert_questionnaire_v2_to_v3.py`) is provided for offline conversion of v1 and v2 files. The JavaScript library does not implement v1/v2 import.

The principal breaking changes are:

- `page_id` is renamed to `category`.
- `prompt` is renamed to `question`.
- `textarea_rows` is renamed to `rows`.
- `visible_if_question_id` is renamed to `visible_if_id`.
- Several fields are removed: `title`, `description`, `predefined_text`, `checkbox_label`, `allow_freetext`, `order`, `has_status`, `multiline`, `visible_if_operator`, `visible_if` (JSON), `rule_on_value`, `rule_status`, `review_status_by_rule`, `reviewer_question`.
- `reviewer_question: true` is replaced by `type: "review"`.
- The concept of "mode" is replaced by the "role" + "view" two-axis system.

### 2.1 Migration Script Field Mappings

The Python migration script applies the following transformations:

| Source field | V3 field | Notes |
| --- | --- | --- |
| `prompt` | `question` | |

| `visible_if_question_id` | `visible_if_id` | |
| `page_title` | _(dropped)_ | category is the title |
| `order` | _(dropped)_ | row position determines order |
| `predefinedText` / `predefined_text` | _(dropped)_ | |

| `allow_freetext` | _(dropped)_ | |

| `review_status_by_rule` | _(dropped)_ | |
| `visibleIf` (camelCase) | `visible_if_id` / `visible_if_value` | |

Unknown fields are preserved and appended after the known v3 fields, in their original order.

## 3. Goals

- Provide a lightweight embeddable `javascript + css` library.
- Run entirely in static HTML with no backend and no build step.
- Use a flat tabular question format as the primary import/export format.
- Import and export questions as CSV directly from the browser.
- Import and export questions as JSON directly from the browser.
- Provide a Python migration script that converts v1 and v2 questionnaire files to v3 format.
- Preserve unknown extra question fields during import/export.
- Allow top-level questionnaire metadata to be configured programmatically in HTML.
- Expose a documented API for role switching, view switching, category navigation, loading, saving, and answer access.
- Support a hook that runs on every user change for ad hoc visibility, rules, and derived values.
- Support `interviewed`, `reviewer`, and `editor` roles.
- Support `normal`, `tabular`, `overview`, and `template` views.
- Encode navigation state in the URL hash for deep linking and browser history.
- Allow question card rendering to be customized through Mustache.js templates.
- Provide a built-in template editor with syntax highlighting for all templates and the `onChange` hook.
- Display reviewer comments to interviewed users in a visually distinct style.
- Provide a weighted reviewer scoring model with a per-category and total summary panel.

## 4. Non-Goals

- No backend, database, or remote API.
- No authentication or user management.
- No collaborative real-time editing.
- No requirement for a JavaScript build toolchain.
- No requirement that all questionnaire UI be generated by the library.
- No requirement that host applications use the default templates.

## 5. Roles and Views

### 5.1 Interviewed Role

The interviewed role is for the person answering ordinary questionnaire questions.

In interviewed role:

- normal questions are shown with editable answer controls,
- `review`-type questions are hidden,
- review status controls are hidden,
- reviewer comments (if present) are displayed below each question answer in a distinct blue style (`.q-reviewer-comment`).

### 5.2 Reviewer Role

The reviewer role is for validation and review.

In reviewer role the displayed questions depend on the view:

- **`normal` view** shows only the non-`review` questions, with answer controls read-only, so the reviewer can read the interviewee's answers and add reviewer comments.
- **`overview` view** shows only the `review`-type questions, with editable answer controls and review status controls, alongside the reviewer summary panel.
- **`tabular` view** shows every question in a read-only table.

Across all reviewer views:

- normal answer controls are read-only; `review`-type answer controls are editable,
- reviewer comments are editable for every displayed question,
- the `analysis` field is shown for questions that have it,
- `review`-type question cards are visually highlighted (`.q-reviewer-card`).

### 5.3 Editor Role

The editor role is for changing the questionnaire definition itself.

In editor role, the app allows an authorized local user to:

- edit existing question rows,
- rearrange questions,
- add new questions,
- delete questions,
- import questions from CSV or JSON,
- export questions to CSV or JSON,
- edit Mustache templates and the `onChange` hook code.

The editor role has access to all four views.

### 5.4 Views

A **view** controls how data is presented independently of the role.

#### Normal View

Shows question cards as in the interviewed experience. In editor role, each card has a per-question **Edit** button that opens the full editor form for that question.

#### Tabular View

Shows questions as a scrollable table where each field is a column. Available in reviewer and editor roles. See section 11.2 for full details.

#### Overview View

Shows questions with a sticky reviewer summary panel below the category navigation. Available in reviewer and editor roles. See section 9 for full details.

#### Template View

Shows a code editor for Mustache templates and the `onChange` hook. Available in editor role only. See section 11.3 for full details.

### 5.5 Role × View Availability Matrix

| View | interviewed | reviewer | editor |
| --- | --- | --- | --- |
| `normal` | ✓ | ✓ | ✓ |
| `tabular` | — | ✓ | ✓ |
| `overview` | — | ✓ | ✓ |
| `template` | — | — | ✓ |

The default view for each role:

- `interviewed` → `normal`
- `reviewer` → `overview`
- `editor` → `tabular`

Switching the role (via `setRole` or the role selector) activates that role's default view. Deep links (`navigateTo`, `setAnchor`, and the URL hash) may specify any view that is valid for the role.

### 5.6 Configurable Role Labels

The internal role ids must be stable: `interviewed`, `reviewer`, `editor`.

Displayed labels are configurable in HTML:

```js
const app = QuestionnaireV3.create({
  roleLabels: {
    interviewed: "Applicant",
    reviewer: "Validator",
    editor: "Designer"
  }
});
```

## 6. High-Level Architecture

The solution consists of:

- a browser JavaScript library (`questionnaire_v3.js`),
- a default CSS stylesheet (`questionnaire.css`),
- host HTML that defines the application shell,
- host-provided Mustache templates for question cards and editor forms,
- optional Python tooling for assembling a single HTML file or migrating data.

The JavaScript library manages:

- normalized questionnaire data,
- question rendering into host-selected containers,
- answer state,
- review state,
- category navigation,
- role switching,
- view switching,
- anchor-based URL hash navigation,
- import/export,
- editor operations,
- hooks and change notifications,
- the reviewer summary panel,
- the template editor.

The host HTML defines:

- the questionnaire header,
- toolbar layout,
- role switch controls,
- view switch controls,
- category navigation controls,
- import/export buttons,
- app containers,
- initial Mustache templates.

## 7. Data Model

### 7.1 Question Fields

The standard v3 question fields are listed below. Fields marked **required** must be present. Fields marked **optional** may be omitted.

| Field | Status | Type | Notes |
| --- | --- | --- | --- |
| `id` | required | string | Unique question identifier. Must not contain dashes. Use underscores. |
| `category` | optional | string | Groups the question into a named section. Doubles as the section title. Defaults to `"default"`. Must not contain dashes. |
| `subcategory` | optional | string | Informational sub-grouping. Shown in small text beside the question card. |
| `question` | optional | string | Primary question text shown to the user. |
| `help` | optional | string | Additional explanation or guidance shown below the question. |
| `required` | optional | boolean | If true, the question must be answered when visible. Default `false`. |
| `default` | optional | any | Value used when the answer is empty. Also used as the answer when the question is hidden (for visibility evaluation of dependent questions). |
| `type` | optional | string | UI control type. See section 7.2. Default `"text"`. |
| `rows` | optional | number | Height of textarea in rows. Minimum 1. When unset, `text` questions render as a single-line input. If set greater than 1, the text control becomes a multiline `<textarea>`. |
| `options` | optional | array or JSON string | Array of option objects for `radio`, `dropdown`, and similar types. Each option has `value`, `label`, and optional extra fields. `is_other` marks the free-text option. |
| `visible_if_id` | optional | string | ID of the controlling question for simple conditional visibility. |
| `visible_if_value` | optional | string | Visibility expression evaluated against the controlling question's answer. See section 7.4. |
| `answer` | optional | any | Current answer value. |
| `review_status` | optional | string | Review status for `review`-type questions: `pending`, `satisfactory`, `partial`, `unsatisfactory`. |
| `reviewer_comment` | optional | string | Reviewer note. Available and visible for all question types. |
| `weight` | optional | number | Scoring weight for `review`-type questions. Default `1`. |
| `weight_score` | — | number | Always recalculated from `review_status` × `weight`. Ignored on import. Not a persisted field. |
| `analysis` | optional | string | Analysis note shown in reviewer role. |

Fields removed from v2 and their replacements:

| Removed field | Reason / replacement |
| --- | --- |
| `prompt` | Renamed to `question` |
| `page_id` | Renamed to `category` |
| `textarea_rows` | Renamed to `rows` |
| `visible_if_question_id` | Renamed to `visible_if_id` |
| `title`, `description` | Removed; use `question` and `help` |
| `predefined_text` | Removed |
| `checkbox_label` | Removed; use `options[0].label` or `question` |
| `allow_freetext` | Removed; use `yes_or_text`, `no_or_text`, or companion `text` question with `visible_if` |
| `order` | Removed; position in the flat list determines display order |
| `has_status` | Removed; only `review`-type questions have review status |
| `multiline` | Removed; `rows > 1` implies multiline |
| `reviewer_question` | Removed; replaced by `type: "review"` |
| `visible_if_operator` | Removed; operator is embedded in `visible_if_value` expression |
| `visible_if` (JSON) | Removed; use `visible_if_value` expression syntax or `onChange` hook |
| `rule_on_value`, `rule_status` | Removed; implement in `onChange` hook |
| `review_status_by_rule` | Removed |

### 7.2 Question Types

| Type | Renders | Notes |
| --- | --- | --- |
| `text` | Text input or textarea | `rows > 1` renders a `<textarea>` |
| `checkbox` | Single checkbox | Boolean answer |
| `yes_or_no` | Yes / No radio buttons | Boolean answer stored as `true` or `false` |
| `yes_or_text` | Yes / No radio buttons + text input | Answer is `true` when Yes; `false` or text when No; text input visible when No |
| `no_or_text` | Yes / No radio buttons + text input | Answer is `false` when No; `true` or text when Yes; text input visible when Yes |
| `radio` | Radio button group | Uses `options` array |
| `dropdown` | Select element | Uses `options` array; option with `is_other: true` may show a companion text input if a following `text` question is shown via `visible_if` |
| `info` | Read-only `<pre>` block | Renders `answer` value as preformatted text; no input control |
| `html` | Read-only `<div>` block | Renders `answer` as HTML; see sanitization note in section 7.2.1 |
| `review` | Reviewer-only scored question | Has `review_status` and `weight`; hidden in the interviewed role and reviewer `normal` view; shown in reviewer `overview` and the editor role; cards are highlighted |
| `ignore` | Not rendered | Question is completely skipped in all views; useful as a documentation or placeholder row |

#### 7.2.1 HTML Type Sanitization

The `html` type renders `answer` content inside a `<div>`. Implementations must document their sanitization behavior. The recommended defaults:

- Host-authored HTML set programmatically is treated as trusted and rendered as-is.
- HTML imported from external files should be escaped unless explicitly configured otherwise.

Host applications must understand the security implications of rendering untrusted HTML.

#### 7.2.2 Yes/Or/Text Types

For `yes_or_text`, the answer is:
- `true` (boolean) when the user selects Yes, OR
- `false` (boolean) when the user selects No and provides no additional text, OR
- a non-empty string containing the user's text when the user selects No and fills in the text input.

The companion text input is shown when No is selected. When `rows > 1` the input renders as a `<textarea>` with that many rows; otherwise it renders as a single-line text input.

For `no_or_text`, the answer is:
- `false` (boolean) when the user selects No, OR
- `true` (boolean) when the user selects Yes and provides no additional text, OR
- a non-empty string containing the user's text when the user selects Yes and fills in the text input.

The companion text input is shown when Yes is selected. The same `rows` rule applies.

**Boolean string normalisation** applies universally across all types: the string values `"yes"` and `"true"` (case-insensitive) are treated as boolean `true`; the string values `"no"` and `"false"` (case-insensitive) are treated as boolean `false`. This applies during import, answer setting, and visibility evaluation.

### 7.3 Category

`category` replaces `page_id` from v2. It serves simultaneously as the page key and the page display title, which means category values must be unique across the questionnaire.

- Categories are auto-derived from question rows. No separate category configuration is needed.
- The order of categories follows the order of first appearance in the flat question list.
- If a question has no `category`, it is assigned to `"default"`.
- If all questions belong to a single category, the category navigation controls should not be shown by the default UI. Host HTML may still render custom category controls.
- Category values must not contain dashes (`-`). Use underscores or spaces.

**Dash in category warning**: if a category value containing a dash is encountered — on import, on question add, or on question edit — the runtime must:
1. Display an alert warning the user that the category value contains a dash and that it will be replaced with an underscore.
2. Replace all dashes in the category value with underscores and continue.

Example: given questions with categories `["basics", "basics", "details", "basics"]`, two categories are created: `basics` (appears first, contains three questions) and `details` (contains one question).

### 7.4 Visibility Expression Syntax

Simple conditional visibility is controlled by two fields:

- `visible_if_id`: the ID of the controlling question.
- `visible_if_value`: an expression evaluated against the controlling question's current answer.

If `visible_if_id` is empty or not set, the question is always visible (subject to its `type` — `ignore` is always hidden).

When the controlling question is itself hidden, its `default` value is used in place of the actual answer for evaluation.

All string comparisons in visibility expressions are **case-insensitive**.

#### Expression Syntax

| Expression | Meaning |
| --- | --- |
| `value` | answer equals `value` (case-insensitive) |
| `!value` | answer does not equal `value` |
| `a\|b\|c` | answer equals `a`, `b`, or `c` (alternatives; leading/trailing whitespace trimmed per token) |
| `!a\|b\|c` | answer does not equal any of `a`, `b`, `c` |
| `true` | answer is boolean `true`, or the strings `"true"` or `"yes"` (case-insensitive) |
| `false` | answer is boolean `false`, or the strings `"false"` or `"no"` (case-insensitive) |
| `other` | answer equals `"other"` OR answer value is not present in the question's `options` list. An empty or unanswered value never matches `other`. |

#### Examples

```
visible_if_id: q_accounting_support
visible_if_value: true
```
→ show when `q_accounting_support` answer is `true`, `"true"`, or `"yes"`.

```
visible_if_id: q_employment_status
visible_if_value: self_employed | freelance | contractor
```
→ show when answer is any of those three values (case-insensitive).

```
visible_if_id: q_country
visible_if_value: other
```
→ show when the answer is `"other"` or not in the country options list.

```
visible_if_id: q_has_issues
visible_if_value: !false
```
→ show when answer is not `false` (and not `"false"` or `"no"`).

### 7.5 Extra Fields

Question rows may contain extra fields not defined by this specification.

The runtime must:

- preserve extra fields during import/export,
- keep extra fields attached to the question object,
- expose extra fields to question templates,
- display extra fields in the tabular editor as columns in the optional-fields group.

## 8. Review Model

### 8.1 Review-Type Questions

`type: "review"` identifies a reviewer-only scored question.

- Review-type questions are hidden in the `interviewed` role and in the reviewer `normal` view.
- Review-type questions are shown in the reviewer `overview` view and in the `editor` role (all views) with editable answer controls.
- Review-type questions have a `review_status` field (`pending`, `satisfactory`, `partial`, `unsatisfactory`).
- Review-type questions contribute to the reviewer score calculation using their `weight` field.
- Non-review questions do not have `review_status` controls. Their `review_status` field is ignored in scoring.

### 8.2 Reviewer Comments

`reviewer_comment` is available for every question regardless of type.

- In `reviewer` role: the comment field is editable for all questions.
- In `interviewed` role: if a question has a non-empty `reviewer_comment`, it is displayed below the answer in a visually distinct blue style using the class `.q-reviewer-comment`.
- In `editor` role: the comment field is editable for all questions.
- Reviewer comments are preserved through import/export.

### 8.3 Status Values

The four review status values and their default display properties:

| Status | Default label | Default RAG color | CSS class |
| --- | --- | --- | --- |
| `pending` | Pending | Blue | `.q-status-pending` |
| `satisfactory` | Satisfactory | Green | `.q-status-satisfactory` |
| `partial` | Partial | Amber | `.q-status-partial` |
| `unsatisfactory` | Unsatisfactory | Red | `.q-status-unsatisfactory` |

The host application may configure display labels via initialization options:

```js
QuestionnaireV3.create({
  statusLabels: {
    pending:        "?",
    satisfactory:   "OK",
    partial:        "WARN",
    unsatisfactory: "ERR"
  }
});
```

Colors may be overridden via CSS variables (see section 18). If the template renders only the status key or a label string, no color is applied by default — the host template is responsible for applying the appropriate class.

### 8.4 Score Calculation

Score is calculated for `review`-type questions only.

For each `review`-type question:

| `review_status` | Score factor |
| --- | --- |
| `satisfactory` | 1.0 |
| `partial` | 0.5 |
| `unsatisfactory` | 0.0 |
| `pending` | 0.0 |

The `weight_score` for a question is `weight × score_factor`.

The percentage score for a set of questions:

```
score % = sum(weight_score) / sum(weight) × 100
```

Where `sum(weight)` is the total weight of all `review`-type questions in the set. If total weight is zero, score is undefined.

## 9. Reviewer Summary Panel

The reviewer summary panel is shown in `overview` view for `reviewer` and `editor` roles. In the reviewer `overview` view the question list below the panel contains only `review`-type questions.

### 9.1 Position and Layout

The panel is displayed as a sticky band below the category navigation tabs. It remains visible as the user scrolls through questions.

### 9.2 Content

The panel shows two summary blocks:

**Current category summary:**

- Label: the current category name.
- Count of `review`-type questions per status: satisfactory / partial / unsatisfactory / pending.
- Total count of `review`-type questions.
- Weighted score percentage for this category.
- A RAG (red/amber/green) indicator derived from the score.

**Total summary (all categories):**

- Label: "Total" or equivalent configurable label.
- Aggregate counts per status across all categories.
- Total weighted score percentage.
- Overall RAG indicator.

### 9.3 RAG Thresholds

The summary panel's RAG indicator is configurable. Default thresholds:

| Score range | Indicator | CSS class |
| --- | --- | --- |
| ≥ 80% | Green | `.q-rag-green` |
| ≥ 50% | Amber | `.q-rag-amber` |
| < 50% | Red | `.q-rag-red` |
| No review questions / zero weight | Neutral | `.q-rag-neutral` |

The thresholds may be overridden at initialization:

```js
QuestionnaireV3.create({
  ragThresholds: { green: 80, amber: 50 }   // values in percent
});
```

RAG indicators may be disabled entirely, in which case the summary panel shows only counts and the score percentage with no color coding:

```js
QuestionnaireV3.create({
  ragThresholds: null   // disables RAG coloring
});
```

When RAG is disabled, the summary template receives `_rag: null` and may render counts and percentages in any format — for example, a plain number or an icon.

## 10. Templates and Appearance

### 10.1 Mustache.js

V3 uses [Mustache.js](https://github.com/janl/mustache.js) as the template engine, replacing the v2 pseudo-Mustache implementation.

Mustache.js must be loaded before the questionnaire library. The recommended CDN source:

```html
<script src="https://unpkg.com/mustache@latest/mustache.min.js"></script>
```

Alternatively, Mustache.js may be embedded inline in the HTML file.

The library calls `Mustache.render(template, context)` to render each question card.

### 10.2 Question Card Template

The question card template is a Mustache template that renders one question.

The template context includes all question fields plus the following runtime properties:

- `_role` — current role (`interviewed`, `reviewer`, `editor`)
- `_view` — current view (`normal`, `tabular`, `overview`, `template`)
- `_editor` — boolean; true when the current role is `editor`
- `_visible` — boolean; whether the question passes its visibility condition
- `_is_review` — boolean; true if `type === "review"`
- `_category_title` — display title for the question's category
- `_status_label` — configured label for the current `review_status`
- `_analysis_visible` — boolean; true when `analysis` is present and the role is `reviewer` or `editor`
- `_comment_readonly` — boolean; true when the role is `interviewed` and a non-empty `reviewer_comment` exists
- `_errors` — array of validation error strings for this question

The library injects interactive controls into placeholder elements identified by `data-*` attributes:

- `data-question-control` — the answer control (always).
- `data-review-control` — the review status control (filled only for `review`-type questions in `reviewer`/`editor` roles; empty otherwise).
- `data-reviewer-comment-control` — the editable reviewer comment field (filled only in `reviewer`/`editor` roles; empty otherwise).

Use `_comment_readonly` to display the reviewer comment as read-only blue text for interviewed users, and `data-reviewer-comment-control` to expose the editable comment to reviewers and editors.

Example minimal template:

```html
<template id="question-card-template">
  <section class="q-card" data-question-id="{{id}}">
    <div class="q-card-head">
      <h3 class="q-prompt">{{question}}</h3>
      {{#required}}<span class="q-required">*</span>{{/required}}
      {{#subcategory}}<span class="q-subcategory">{{subcategory}}</span>{{/subcategory}}
      {{#_editor}}<button type="button" class="q-edit-btn" data-edit-question="{{id}}">✏️ Edit</button>{{/_editor}}
    </div>
    {{#help}}<p class="q-help">{{help}}</p>{{/help}}
    {{#_analysis_visible}}<p class="q-analysis">{{analysis}}</p>{{/_analysis_visible}}
    <div class="q-answer-block" data-question-control></div>
    {{#_comment_readonly}}<div class="q-reviewer-comment">{{reviewer_comment}}</div>{{/_comment_readonly}}
    <div data-review-control></div>
    <div data-reviewer-comment-control></div>
    {{#_errors}}<p class="q-error">{{.}}</p>{{/_errors}}
  </section>
</template>
```

If no question card template is provided, the library uses an equivalent built-in default.

### 10.3 Reviewer Question Card Template

An optional separate template used for `review`-type questions when in reviewer or editor role. Falls back to the normal question card template if not provided.

```html
<template id="reviewer-question-card-template">
  <section class="q-card q-reviewer-card" data-question-id="{{id}}">
    <div class="q-card-head">
      <h3 class="q-prompt">{{question}}</h3>
      <span class="q-meta-pill q-status-{{review_status}}">{{_status_label}}</span>
    </div>
    {{#analysis}}<p class="q-analysis">{{analysis}}</p>{{/analysis}}
    {{#help}}<p class="q-help">{{help}}</p>{{/help}}
    <div class="q-answer-block" data-question-control></div>
    <div data-review-control></div>
    <div data-reviewer-comment-control></div>
  </section>
</template>
```

```html
    </fieldset>
    <fieldset class="q-editor-section">
      <legend>State</legend>
      <div data-editor-field="answer"></div>
      <div data-editor-field="review_status"></div>
      <div data-editor-field="reviewer_comment"></div>
    </fieldset>
  </form>
</template>
```

Each `data-editor-field="<fieldname>"` slot is replaced with the field's editor control. The form is rendered into a panel opened from a question's Edit button (in normal or tabular view). If no editor form template is provided, the library lays the fields out in a default grid.

### 10.5 Host-Owned Shell

The host HTML defines:

- header markup and title placement,
- toolbar buttons (load/save CSV, load/save JSON, save HTML),
- role selector,
- view selector,
- category navigation,
- render target containers.

The library API makes it straightforward to wire these controls to runtime functions.

## 11. Editor Mode

### 11.1 Normal View With Per-Card Edit Buttons

When the editor role is active and the view is `normal`, question cards are rendered as in the interviewed experience, but each card has an additional **Edit** button.

Clicking Edit:

- opens the full editor form (section 10.4) for that question in a side panel or modal,
- updates the URL hash to `#editor-normal-<question_id>`.

The editor form allows editing all standard fields. Complex fields (`options`, `visible_if_value`) are shown with appropriate input controls. Saving or dismissing the form closes the panel and re-renders the affected question.

### 11.2 Tabular View

The tabular view renders all questions as rows in a scrollable table. Each field is a column. In the `editor` role the cells are inline-editable and the add/move/delete controls are active; in the `reviewer` role the table is read-only.

#### Column Groups

Columns are visually grouped by background color:

| Group | Background | Columns |
| --- | --- | --- |
| Question | Light blue | `id`, `category`, `subcategory`, `question`, `default`, `help`, `answer` |
| UI | Light yellow | `type`, `options`, `rows`, `visible_if_id`, `visible_if_value`, `required` |
| Optional | Light green | `review_status`, `reviewer_comment`, `weight`, `weight_score`, `analysis`, and all extra fields |

Group header cells span all columns in their group.

#### Inline Editing

Simple text, number, and select fields are inline-editable: clicking a cell makes it editable in place.

Complex fields (`options`, `visible_if_value` expressions longer than a short threshold) show a truncated preview. Editing those fields requires opening the full editor form via the Edit button.

#### Per-Row Controls

Each row has the following action buttons in a controls column:

- **↑** — move this question one position earlier in the list
- **↓** — move this question one position later in the list
- **✏️** (Edit) — open the full editor form for this question (same panel as in normal view)
- **🗑️** (Delete) — remove this question after confirmation

#### Search

A 🔍 search field above the table filters visible rows. Matching is case-insensitive across `id`, `question`, and `answer` fields. The search does not change question order or persisted data. When the search field is empty all rows are shown.

#### Add Question

A button above the table adds a new empty question row and opens the editor form for it.

### 11.3 Template View

The template view provides a code editor for all customizable text content. It is available only in editor role.

#### Editable Items

Each item has a stable template ID used in anchor navigation:

| Template ID | Content |
| --- | --- |
| `question_card` | Mustache template for the question card |
| `reviewer_card` | Mustache template for the reviewer question card |
| `editor_form` | Mustache template for the editor form layout |
| `onchange` | JavaScript function body for the `onChange` hook |

The view shows a selector or tabs for switching between items. The selected item is reflected in the URL hash as `#editor-template-<template_id>`.

#### Syntax Highlighting

The template view uses [CodeMirror](https://codemirror.net/) loaded from CDN for syntax highlighting:

```html
<link rel="stylesheet" href="https://unpkg.com/codemirror@5/lib/codemirror.css">
<script src="https://unpkg.com/codemirror@5/lib/codemirror.js"></script>
<script src="https://unpkg.com/codemirror@5/mode/htmlmixed/htmlmixed.js"></script>
<script src="https://unpkg.com/codemirror@5/mode/javascript/javascript.js"></script>
```

Mustache templates use `htmlmixed` mode. The `onChange` hook uses `javascript` mode.

Monaco Editor is an acceptable alternative.

#### Live Preview

Changes in the template editor apply live: the questions view re-renders using the updated template whenever the editor content changes (with a short debounce).

#### Persistence

All template content and the `onChange` hook body are embedded in the saved HTML file (section 14.5). On load, the library reads the embedded templates and restores the code editor content.

## 12. Anchor-Based Navigation

Navigation state is encoded in the URL hash fragment as a dash-separated tuple.

### 12.1 Hash Format

| Format | Example | Meaning |
| --- | --- | --- |
| `#role-view` | `#reviewer-overview` | Role and view only |
| `#role-view-id` | `#reviewer-normal-q_country` | Role, view, and a target identifier |

There is no 4-tuple. A question ID uniquely determines its category, so specifying both is redundant.

### 12.2 Unified ID Namespace

The `id` segment in a triplet is looked up in a unified namespace. The three namespaces do not overlap by design:

| Source | Example values | Effect |
| --- | --- | --- |
| Question IDs | `q_country`, `q_income` | Navigate to that question; infer and activate its category |
| Category values | `basics`, `details` | Navigate to that category without selecting a specific question |
| Template IDs | `question_card`, `reviewer_card`, `editor_form`, `onchange` | Open that template in the template view editor (only meaningful in `editor-template` view) |

### 12.3 Parsing Rules

1. Split the hash on `-`.
2. Consume the first token; match against known roles (`interviewed`, `reviewer`, `editor`).
3. Consume the next token; match against known views (`normal`, `tabular`, `overview`, `template`).
4. Everything remaining (joined back with `-`) is the ID, looked up in the unified namespace.

Because role and view names are fixed strings that do not contain dashes, and question IDs and category values must not contain dashes (see section 12.3.1), parsing is unambiguous.

#### 12.3.1 Dash Constraint

Question IDs and category values must not contain dashes (`-`). Use underscores (`_`) or spaces (URL-encoded as `%20`). Template IDs are library-defined and contain only underscores.

### 12.4 Hash Sync and Browser History

The URL hash is updated automatically on every navigation event:

- role change,
- view change,
- category navigation,
- question selection (where applicable).

Hash updates use `history.pushState` where available so that the browser back and forward buttons navigate role/view/category history. If `pushState` is not available, the implementation may fall back to direct `location.hash` assignment (which adds a history entry in all modern browsers).

### 12.5 Deep-Link Initialization

On page load, if the URL contains a hash, the app initializes to the state encoded in that hash before first render. Fields not present in the hash use configured defaults.

### 12.6 Invalid Anchor Fallback Behavior

Invalid or inconsistent anchors fall back silently:

| Situation | Fallback |
| --- | --- |
| Unknown role | Use configured default role |
| Unknown view | Use default view for the resolved role |
| View not available for role (e.g. `#interviewed-tabular`) | Use default view for that role |
| Unknown ID in triplet | Ignore the ID; navigate to role + view only |
| Template ID used in a non-template view | Ignore the ID |
| Question ID used in `editor-template` view | Ignore the ID |

### 12.7 Navigation API

```js
app.getAnchor();                          // returns current hash string e.g. "reviewer-overview"
app.setAnchor("editor-tabular-q_income"); // navigate to encoded state
app.navigateTo({ role, view, id });       // programmatic navigation; id is optional
```

## 13. Hooks and Derived Behavior

The runtime executes a host-provided `onChange` hook on every user change.

Example:

```js
const app = QuestionnaireV3.create({
  onChange(event, api) {
    const income = Number(api.getAnswer("q_income") || 0);
    const expenses = Number(api.getAnswer("q_expenses") || 0);
    api.setAnswer("q_balance", income - expenses, { silent: true });

    if (income - expenses < 0) {
      api.setReviewStatus("q_balance_review", "partial", { silent: true });
    }
  }
});
```

The hook receives:

- `event.type` — event type (e.g. `"answer"`, `"review_status"`, `"reviewer_comment"`)
- `event.question_id` — ID of the changed question
- `event.field` — changed field name
- `event.value` — new value
- `event.previous_value` — previous value
- `event.role` — current role
- `event.view` — current view
- `api` — reference to the public API

The hook may be used to:

- evaluate ad hoc rules,
- calculate derived values,
- update `info` and `html` question answers,
- update review statuses,
- enforce local business logic.

The `silent: true` option on API calls made inside the hook suppresses re-render and prevents recursive hook invocation.

The `onChange` hook body is editable in the template view (template ID `onchange`). The library wraps the stored body in a function at load time:

```js
onChange: new Function("event", "api", storedOnChangeBody)
```

## 14. Import and Export

### 14.1 CSV Import

CSV import must:

- parse a header row,
- auto-detect the delimiter from the header row; supported delimiters are comma, semicolon, pipe (`|`), and tab,
- map columns to question fields using v3 field names,
- preserve unknown columns as extra fields,
- parse booleans case-insensitively where known fields require them; accepted true values: `true`, `t`, `yes`, `y`, `1`; accepted false values: `false`, `f`, `no`, `n`, `0`,
- parse numbers where known fields require them,
- parse JSON-string fields (`options`) where appropriate,
- report row-level errors clearly.

Row order in the CSV determines question order. An `order` column in the CSV is ignored.

### 14.2 CSV Export

CSV export must:

- export a flat question table,
- include standard fields,
- include extra fields,
- serialize `options` as a JSON string,
- preserve enough information to re-import the questionnaire.

### 14.3 JSON Import

JSON import in the browser must support:

- v3 flat question arrays,
- v3 full questionnaire objects (`{ config, questions }`).

Import of v1 and v2 formats is handled offline by the Python migration script (section 14.6), not by the browser library.

### 14.4 JSON Export

JSON export supports:

- **full** (default) — full v3 object with top-level `config` and flat `questions`,
- **flat** — flat question array only.

```js
app.exportJson({ format: "full" });
app.exportJson({ format: "flat" });
```

### 14.5 HTML Save

Standalone HTML export serializes the current document and replaces embedded data blocks with current config and flat question data. It also embeds the current content of all templates and the `onChange` hook body.

Embedded JSON must be escaped so it cannot terminate script blocks.

The embedded data block format:

```html
<script id="questionnaire-v3-data" type="application/json">
{ "config": {...}, "questions": [...] }
</script>
<script id="questionnaire-v3-templates" type="application/json">
{ "question_card": "...", "reviewer_card": "...", "editor_form": "...", "onchange": "..." }
</script>
```

### 14.6 Python Migration Script

The project includes a Python migration script `convert_questionnaire_v2_to_v3.py` for converting v1 and v2 questionnaire files into v3 format.

The script must support:

- YAML input (v1 and v2 formats),
- JSON input (v1 and v2 formats),
- CSV input (v2 flat format).

Output format is selected from the output file extension:

- `.csv` — flat v3 question table,
- `.json` — full v3 object with `config` and `questions`,
- `.yaml` or `.yml` — same as JSON but in YAML.

The converter must apply all field renames and removals described in section 2.1, including:

- `prompt` → `question`,
- `page_id` → `category`,
- `textarea_rows` → `rows`,
- `visible_if_question_id` → `visible_if_id`,
- `reviewer_question: true` → `type: "review"`,
- `visible_if_operator` + `visible_if_value` → merged `visible_if_value` expression,
- removal of `order`, `has_status`, `multiline`, `rule_on_value`, `rule_status`, `review_status_by_rule`, etc.

Unknown fields are preserved and written after the known v3 fields in the output.

## 16. Validation

The runtime must validate:

- question IDs are unique,
- question IDs and category values do not contain dashes,
- referenced question IDs in visibility conditions exist,
- `radio` and `dropdown` questions define valid options,
- required visible questions are answered (on submit/validate call),
- JSON strings in CSV `options` fields parse correctly,
- `review_status` values are from the known set if status labels are restricted,
- loaded v1 and v2 structures can be normalized or produce clear errors.

Validation errors are available through `app.validate()` and are exposed to question templates via `_errors`.

## 17. Accessibility

The rendered questionnaire must follow basic accessibility requirements:

- labels associated with all inputs,
- keyboard-accessible navigation between categories and questions,
- semantic grouping of radio options using `<fieldset>` and `<legend>`,
- visible indication of required fields,
- readable focus states,
- accessible editor forms and tabular view,
- accessible import/export controls,
- accessible review status controls.

Host-provided templates must preserve these requirements.

## 20. Acceptance Criteria

The specification is satisfied when:

1. A static HTML page can embed the library without a build step.
2. The library initializes from a flat v3 question array.
3. The library imports and exports CSV in the browser (v3 format only).
4. The library imports and exports JSON in the browser (v3 format only).
5. Unknown extra question fields survive import/export.
6. Categories are auto-derived from question rows; no separate category configuration is required.
7. A dash in a category value triggers an alert and is auto-replaced with an underscore.
8. Role labels and status labels are configurable in host HTML.
9. Host HTML uses documented API methods for role switching, view switching, category navigation, loading, saving, and answer access.
10. The `onChange` hook runs on every user change and can update derived values.
11. `info` questions render answer text in a `<pre>`.
12. `html` questions render answer HTML in a `<div>` with documented sanitization behavior.
13. The application shell and header are defined in HTML and not generated by JavaScript.
14. Question cards are rendered using Mustache.js with host-provided templates.
15. `yes_or_no` questions render as Yes/No radio buttons storing a boolean value.
16. `yes_or_text` questions show a companion text input when No is selected (answer is `false` or a non-empty string).
17. `no_or_text` questions show a companion text input when Yes is selected (answer is `true` or a non-empty string).
18. `ignore`-type questions are not rendered in any view.
19. `review`-type questions are hidden in the interviewed role and reviewer `normal` view, shown with status controls in reviewer `overview` and the editor role, and their cards are highlighted.
20. The reviewer `normal` view shows only non-review questions; the reviewer `overview` view shows only review questions.
21. Reviewer comments are editable in reviewer and editor roles and displayed in blue to interviewed users.
21. The reviewer summary panel (overview view) shows per-category and total counts per status and a weighted score percentage with a configurable RAG indicator.
22. RAG thresholds are configurable; RAG coloring can be disabled entirely.
23. Review status display labels are configurable (e.g. OK / WARN / ERR / ?).
24. Reviewer and editor roles — tabular view: questions are shown in a table with column groups (question/UI/optional) and 🔍 search; in the editor role the cells are inline-editable with per-row ✏️/🗑️/↑/↓ controls, and the reviewer role sees the same table read-only.
25. Editor role — template view: all Mustache templates and the `onChange` hook body are editable with syntax highlighting via CodeMirror loaded from CDN.
26. The URL hash encodes role + view (2-tuple) or role + view + id (3-tuple) and updates on every navigation event.
27. On page load the app initializes to the state encoded in the URL hash.
28. Invalid hash combinations fall back silently to valid defaults.
29. A Python migration script converts v1/v2 YAML, JSON, and CSV files to v3 format, preserving unknown fields after known fields.
